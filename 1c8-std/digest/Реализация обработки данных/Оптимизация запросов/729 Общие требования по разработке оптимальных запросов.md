# Общие требования по разработке оптимальных запросов (#std729)

**Суть.** Запрос должен быть адекватен решаемой задаче.

**Не надо**
- Выбирать все поля «на всякий случай» — `ВЫБРАТЬ *` (1.1).
- Любой ценой переносить задачу в СУБД: простые запросы эффективнее сложных (2).
- Неоправданно усложнять запрос: для сложных запросов СУБД вероятнее выберет неверный план (2.2).
- Вложенные запросы только ради читаемости (2.2).
- Сложные условия соединения и `ГДЕ`, особенно с подзапросами и `ВЫБОР` (2.2).

**Совет**
- Минимизировать объём выборки: брать ровно нужные данные (1.1).
- Переложить обработку на базу данных вместо выборки большого объёма (1.1).
- Минимизировать в большинстве случаев число запросов к СУБД (1.2).
- Рассмотреть альтернативы: частные тексты запроса вместо универсального, постобработка на
  сервере (2.1).
- Использовать минимально нужное число таблиц: много бывает уже 5–7 (2.2).
- Убедиться в эффективности планов выполнения (2.2).

См. также: 436 (однотипные запросы), 655 (вложенные запросы), 656 (подзапросы в соединении),
732 (динамические списки).
