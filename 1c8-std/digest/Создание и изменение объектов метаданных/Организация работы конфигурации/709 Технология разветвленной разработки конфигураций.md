# Технология разветвленной разработки конфигураций (#std709)

**Суть.** Плановая версия развивается в основном хранилище, исправительная — в своём, каждый
технический проект — в отдельном; вся статья — методическая рекомендация.

**Обязательно**
- В комментарии закладки при исправлении ошибки обязательно указывать её номер и краткое
  наименование в системе баг-трекинга (3.4).
- Перед закладкой изменений в основное хранилище ответственный обязательно запускает проверку
  конфигурации с максимальными настройками; закладка — только после исправления всех ошибок,
  привнесённых проектом (4.8).

**Не надо**
- Копировать основное хранилище под исправительную версию: для каждой создают новое хранилище на
  основе конфигурации последней выпущенной версии (2.1).
- Объёмные доработки в исправительной версии: иначе пересматривают сроки выпуска плановой (2.2).
- Закладка не полностью отлаженной функциональности: основное хранилище всегда готово к сборке
  плановой версии (3.2).
- Переносить изменения по проекту несколькими закладками: на несколько переносов открывают
  несколько проектов (3.5).
- Надолго захватывать объекты основного хранилища при внесении проекта: сначала хранилище проекта
  обновляют до основного, при необходимости итеративно, и лишь когда отличия сведутся к изменениям
  проекта, начинают перенос (4.6).

**Совет**
- Проекты и список ошибок вести в `Системе проектирования прикладных решений (СППР)` (1).
- Все закладки в оба хранилища снабжать комментарием, требования к ним одинаковы (2.3, 3.4).
- В комментарии называть: при встраивании библиотеки — её название и точный номер версии, при
  встраивании технического проекта — номер и краткое наименование, при работе по проекту в
  основном хранилище — ещё и описание изменений закладки (3.4).
- Все изменения исправительного релиза синхронно повторять в основном хранилище; новые объекты и
  реквизиты переносить только сравнением и объединением конфигураций: иначе разойдутся внутренние
  идентификаторы (2.4).
- При сборке версии ставить метку с номером сборки на закладке той версии хранилища, которая идёт
  в сборку (2.5, 3.7).
- Плановые версии вести в основном хранилище; в нём допустимы исправление ошибок без
  перепроектирования, встраивание версий библиотек и отлаженных проектов, в исключительных
  случаях — массовый рефакторинг (3.1, 3.3).
- Ошибку, требующую больших переработок или пересмотра проектных решений, исправлять в рамках
  технического проекта, тем же порядком, что другие проекты (3.3).
- Каждая закладка переводит конфигурацию из одного готового к выпуску состояния в другое (3.2).
- После переноса исправлять наведённые проектом ошибки, а для пересмотра проектных решений
  открывать новый проект (3.6).
- Каждый технический проект вести в отдельном хранилище; при `СППР` оно создаётся
  автоматически (4.1).
- В хранилище проекта правило «Объект поставщика, не редактируется» менять на «Объект поставщика
  редактируется с сохранением поддержки» только у изменяемых объектов; для смены правил достаточно
  захватить корень конфигурации (4.2).
- Периодичность обновления конфигурации хранилища проекта ответственный определяет сам (4.3).
- Сроки тестирования и внесения проекта согласовывать; проекты на много объектов вносить ближе к
  концу разработки (4.4).
- Вносить проект после отладочного тестирования, сформировав файл сравнения конфигураций проекта и
  основного хранилища (4.5).
- После внесения разработчики с тестировщиками проверяют, что перенос корректен и не задел
  смежную функциональность (4.7).
- После переноса изменений хранилище проекта удалять (4.9).
- Номер сборки повышать в основном и исправительном хранилище перед сборкой релиза и при закладке
  обработчика обновления базы (только на `Библиотеке стандартных подсистем`) (5.1).
- Обработчик обновления добавляют в проекте — номер повышают в основном хранилище при переносе;
  ошибку правят в одном хранилище — номер растёт в нём, в двух — в обоих (5.2.1).
- Обработчик обновления и повышение номера сборки класть одной закладкой, привязывая обработчик к
  этому номеру (5.2.2).
- Когда обработчики обновления разбиты по технологическим подсистемам, повышать номер сборки и
  подсистемы, и конфигурации (5.2.3).
- Номер сборки менять в свойствах конфигурации и в процедуре
  `ОбновлениеИнформационнойБазы<ИмяБиблиотеки>.ПриДобавленииПодсистемы` — только на `Библиотеке
  стандартных подсистем` (5.3).
- Хранилище проекта создавать по приложению 1: обновить конфигурацию из основного хранилища,
  создать файл поставки, загрузить его в базу проекта, создать хранилище, завести
  `ТолькоПросмотр` без права захвата и пользователей проекта (1, 2, 3, 4, 5, 6).
- Обновляя хранилище проекта до основного, сравнить основную конфигурацию с конфигурацией
  поставщика и сохранить отчёт (4, рис.), обновить конфигурацию файлом поставки с фильтром
  «Показывать только дважды измененные свойства» (5, рис.), новым объектам поставщика —
  «Объект не редактируется», остальным — «Сохранять текущий режим» (6, рис.), повторить затёртые
  изменения проекта, снова сравнить и сверить отчёты (7, 8, 9, 10).
