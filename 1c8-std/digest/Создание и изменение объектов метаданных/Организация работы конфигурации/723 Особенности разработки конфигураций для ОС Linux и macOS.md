# Особенности разработки конфигураций для ОС Linux и macOS (#std723)

**Суть.** Для Linux и macOS особых мер не нужно; Windows-технологии заменяют кроссплатформенными.
Управляемое и обычное приложение.

**Обязательно**
- Ключевые функции и работу с файловой системой строить на унификации платформы; имя (путь) файла
  во всех местах кода — в одном регистре: в Linux имена регистро-зависимые (2, 2.5, 2.5.1).
- Вместо COM (`COMОбъект`) — кроссплатформенные механизмы: `АдминистрированиеСервера` через ras
  вместо `v83.ComConnector`, `РабочийКаталогДанныхПользователя`, `КаталогДокументов`,
  `КаталогВременныхФайлов` для каталогов; иначе — альтернативы COM, например Native API (2.1).
- Внешние компоненты конфигурации разрабатывать технологией Native API, а картинки WMF и EMF —
  растровыми (PNG, JPG) (2.2, 2.4).
- Для механизмов на объекте `Почта` — `ИнтернетПочта` либо внешние компоненты к почтовым
  клиентам Linux и macOS (2.3).

**Не надо**
- Указывать разделитель пути и маску всех файлов вручную («/», «*.*»): есть
  `ПолучитьРазделительПути` и `ПолучитьМаскуВсеФайлы` (2.5.2).

**Совет**
- Второстепенные (сервисные) функции допустимо отключать в Linux и macOS: их команды скрывать из
  командного интерфейса, а если нельзя — выводить «<Операция> доступна только при работе в ОС
  Windows» (3).
- При `Библиотеке стандартных подсистем` — `ОбщегоНазначения`/`ОбщегоНазначенияКлиент` для имён
  файлов и `ЭтоLinuxКлиент`, `ЭтоMacOSКлиент`, `ЭтоWindowsКлиент` для ОС (2.5.2, 3).
