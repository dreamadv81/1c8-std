# Ограничения на регламентные задания при работе в модели сервиса (#std760)

**Суть.** В модели сервиса по технологии 1cFresh разделённых заданий не бывает: регулярный код
выполняет очередь заданий.

**Обязательно**
- Регулярное выполнение кода в приложениях разделённой базы строить на подсистеме БТС «Очередь заданий»
  либо на своём аналогичном механизме (2).
- Задание с единым для базы расписанием заводить предопределённым, исключив из общих реквизитов,
  разделяющих данные, и добавив имя метода в `ПриПолученииСпискаШаблонов` модуля
  `ОчередьЗаданийПереопределяемый` (2.1).
- Задание с индивидуальным для области данных расписанием заводить непредопределённым, исключив из
  разделяющих реквизитов, с псевдонимом обработчика в `ПриОпределенииПсевдонимовОбработчиков`; включение
  опции добавляет или включает задание (`ДобавитьЗадание`, `ИзменитьЗадание`), выключение — удаляет или
  отключает (`УдалитьЗадание`, `ИзменитьЗадание`) (2.2).
- Задание от имени определённого пользователя создавать
  `РегламентныеЗаданияСервер.ДобавитьЗадание`, передав имя пользователя в параметрах (2.3).
- Управлять заданиями только программным интерфейсом БСП — модулем `РегламентныеЗаданияСервер` (3).
- Учитывать, что «Очередь заданий» не гарантирует выполнение точно по расписанию: точность зависит от
  числа заданий, длительности выполнения и числа исполняющих потоков —
  константы «Максимальное количество исполняющихся фоновых заданий» (4).
- Когда сценарий подразумевает оперативную реакцию, которую очередь не обеспечивает, рассмотреть другие
  решения (4.2).
- Серверная логика такого обновления должна выполняться максимально быстро и только в объёме, нужном
  конкретному пользователю (4.2).

**Не надо**
- Регламентные задания, включённые в состав любого из разделителей: при большом числе областей данных
  перегружают рабочие процессы базы (1).
- Задавать имя пользователя заданию, добавленному менеджером регламентных заданий (2.3).
- Участки, где заданиями управляют из программного кода напрямую (3).
- Предоставлять пользователям сервиса настройку расписания заданий — в общем случае (4.1).
- Использовать регламентное задание там, где есть возможность получать push-уведомления от системы
  обмена: данные загружают по уведомлению, отправляют при потребности (4.2).

**Совет**
- Когда push-уведомлений нет, оставить задание с доступной очереди периодичностью и организовать
  оперативный обмен, когда пользователь работает в рабочем месте, где ждёт обновления (4.2).
- Серверный вызов такого обновления выполнять в длительной операции (4.2).

См. также: 642 (длительные операции).
